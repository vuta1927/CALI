- IOS-007 slice 3: content on the outbox, applying pulled content, conflict decisions (iOS only; no API/contract change).
  - **Push of content:** `ContentOutbox` queues dirty plans, activations, phases, workouts, planned exercises, goals and body measurements as contract payloads, parents first, in the same transaction as `ContentStore.apply` and at the start of each sync run (so bundled, imported and earlier rows go out once there is an account). A row whose payload equals the last one queued is not queued again; soft deletes send `{id, deletedAt}`; a workout or exercise removed from a plan sends a delete (children first) only if the server may know it; `dirty` is cleared when the acknowledgement still matches the row. `planned_workouts.focus` is not in the contract and stays on the device.
  - **Pull applies:** `ContentApplier` writes `sync_inbox` rows into the content tables (any order within a page; unknown parent, unknown exercise, undecodable target, out-of-range weight stay in the inbox). A change waits while this device has an edit of that entity in flight; stale changes (older than an acknowledged version) are dropped. The app reloads its content after an apply.
  - **Decisions (Profile → Đồng bộ):** conflict → "Giữ bản trên máy" (same change, new mutation on the server's version, same queue position) or "Dùng bản máy chủ" (content entities only; drops this device's pending changes of that entity); rejected → "Gửi lại" (e.g. after pausing a plan for `active_plan_limit`) or "Bỏ qua". Fixed sentences per code (`active_plan_limit`, `plan_count_limit`, `pinned_goal_limit`, `goal_unlock_cycle`); body-measurement conflicts never show the value outside the body screen.

- B3 backend BE-004 (code + tests, reviewed; PO accepted ADR-070 on 2026-11-09): `GET /v1/sync/pull?cursor&limit`. The feed is the user's own change history in `seq` order, one row per version (including the pulling device's own pushes, so applying a page is an idempotent upsert), with `Cache-Control: no-store`. `limit` is 1..100 (default 100). `cursor`, `nextCursor` and every `changeId` are one opaque token, `seq` plus `userId` signed with HMAC-SHA256 (76 characters), so a `changeId` can be passed as `cursor` and an empty page returns the position unchanged. A malformed, altered, differently-keyed or other-user cursor, a bad `limit` or a repeated parameter is 400 (not 401, which is for tokens). 410 `cursor_expired` when the cursor is ahead of the feed (for example after a restore), points at a change no longer in the log, or is older than `Sync:ChangeLogRetentionDays` (default 180); the initial pull without a cursor is never rejected for age. Writers allocate `seq` under the `user_sync_state` lock until commit (ADR-069), so concurrent pushes never make a page skip a change. New secret `Sync__CursorSigningKey` (base64, at least 32 bytes; required outside Development, where it is derived from the dev token key if unset). - B2 backend BE-003 (code + tests, reviewed; PO accepted ADR-069 on 2026-11-09): `POST /v1/sync/push`. The whole push is one READ COMMITTED transaction and each mutation runs in its own savepoint, in batch order, so a rejected or conflicting mutation does not undo the others. The push locks the user `FOR SHARE`, registers the device and locks `user_sync_state` `FOR UPDATE` first, so `sync_change_log` sequence numbers stay gap-free across concurrent pushes. Receipts are idempotent per `(user, mutationId)` with a fingerprint over `{entityType, entityId, action, baseVersion, payload}` (`clientChangedAt` excluded) using the ADR-068 canonical JSON hash, not RFC 8785 as docs/08 and ADR-031 said. A replay returns `duplicate` with the stored receipt; the same `mutationId` with a different fingerprint is `mutation_id_reused`. Receipts for `dependency_missing` (retryable), `mutation_id_reused` and `forbidden_entity` are not stored. All `SyncEntityType` values are writable, including `plan_activation`, `plan_phase`, `plan_goal` and `body_measurement`; `baseVersion` mismatches return `conflict` with the server entity; a missing parent returns a retryable `dependency_missing`; another user's id is rejected without leaking it; retired exercises stay referenceable (FK only). A malformed batch or envelope (invalid JSON, 0 or more than 100 mutations, missing or unknown fields) is 400 `validation_failed` for the whole request before anything is written; an unknown `entityType` gets a per-mutation `forbidden_entity` receipt instead. Other errors: 401, 404 `user_not_found`, 409 `device_owner_mismatch`, 413 (over 1 MiB), 415, 429 (`sync` policy). Device registration uses `INSERT ... ON CONFLICT DO NOTHING` without a conflict target plus an owner-scoped `UPDATE`, because `devices` has two unique indexes and `ON CONFLICT (id)` raised 23505 when a new device sent concurrent first pushes. OpenAPI: `SyncMutation.entityType` is now a string of 1..64 characters (the `SyncEntityType` enum stays as the list of writable types), `SyncPushRequest` is closed (`additionalProperties: false`), new 404/413/415 responses, `forbidden_entity` documented as not persisted.
